--- Icon concept --------------------------------------------

--- Banknote inspiration: Tunisian dinar (TND) --------------

The green banknote in the icon should evoke the design language
of Tunisian dinar bills, not a generic US dollar bill.

Concretely:
  Color:     Green/teal matching the 5 TND note. Muted,
             desaturated. NOT dollar-bill green. Suggested hex
             #6B9080 — a sage-teal that reads as "money"
             universally while sitting authentically in the TND
             color family.
  Border:    Subtle geometric arabesque border around the
             banknote edge — a nod to the traditional Tunisian
             engraving patterns on real TND notes.
  Center:    Abstract suggestion of a portrait medallion (real
             TND bills have a historical figure). At icon size
             this reads as a soft circle/oval inside the bill.
             Do NOT attempt a real face.
  Corner:    Optional — a small circular medallion shape where
             a denomination number would be on a real bill.
             Only include if legible at 48dp.

Design rule: at 48dp, only two things must read clearly:
  1. It's a wallet.
  2. A banknote is sticking out.
Everything else is bonus at larger sizes.

Do NOT copy:
  - Actual TND bill artwork, portraits, or serial numbers
  - Any real currency's exact layout
  - US dollar, Euro, or generic international bill styling
  - Ivy's leaf icon or its green

CRITICAL: The wallet must NOT look related to Ivy Wallet's leaf
icon. If a bystander sees both icons side by side, they must not
think they belong to the same app.

Deliberately NOT green as the primary accent. Both Ivy Wallet

--- Spendaily core principles extracted ---------------------

   The safe-to-spend number is the hero. Everything else is

   above the fold.

   No gradients, no mascots, no gamification, no decoration.
   Ivy's own visual language is already calm. Don't fight it.

   Every UI element answers "what can I do now?" — not
   "here is everything."

   Month grid, day status colors, no numbers.

   Already supported (BudgetPeriodType.Salary from Task 1).
   UI must show "Left until payday" — never a date.

8. KEY CONVENTIONS (locked in)
================================================================

Money:
  - Engine uses Long minor units.
  - New entities use Long minor units.
  - TND has 3 decimals. 100.50 TND = 100_500L.
  - Ivy legacy entities still use Double / BigDecimal.
    Conversion happens only at the mapper boundary via
    CurrencyMinorUnits.
  - Never Float. Never Double for new money fields.

Time:
  - Instant → LocalDate via a ZoneId parameter. Never global.

Allocation invariants (tested):
  - Σ allocation amounts == source amount (exact)
  - Zero-amount days omitted
  - Schedules never create transactions
  - Never double-count: actual accounting vs guidance are
    separate ledgers

Entity style (matches TagEntity):
  - @Keep @Serializable @Entity(tableName="snake_plural")
  - UUID PK: @PrimaryKey @SerialName("id")
    @Serializable(with = KSerializerUUID::class)
  - @SerialName("camelCase") on every column
  - Instant via @Serializable(with = KSerializerInstant::class)
  - isSynced / isDeleted: Boolean = false with @Deprecated
    annotation "Obsolete field used for cloud sync..."

DAO style:
  - Read in dao/read/XxxDao.kt: @Dao interface, @Query only
  - Write in dao/write/WriteXxxDao.kt: @Dao interface, @Upsert
  - NO @Insert(onConflict = ...)
  - Multi-row tables: saveMany WITHOUT deleteAll on import
  - Singleton tables: deleteAll THEN saveMany on import

Test style:
  - JUnit4 (@Test from org.junit.Test)
  - Kotest assertions (io.kotest.matchers.shouldBe etc.)
  - Backtick test names
  - Real objects (no mocks) unless mocking a repository/DAO
  - coEvery / coVerify for suspend DAO functions

CRITICAL GOTCHA discovered in Task 15b-2:
  shouldBeRight() returns the SEALED interface type (Transaction),
  not the concrete subclass. If the test needs to check a field
  that only exists on the subclass (like allocationMode on
  Expense), you must cast:
    (result.shouldBeRight() as Expense).allocationMode shouldBe ...
  Direct .allocationMode on the right of shouldBeRight() fails
  with "Unresolved reference 'allocationMode'".

Backward-compat:
  - The pre-existing 450-150.json backup fixture does not
    contain our new keys. Our fields all have = emptyList() or
    = "TODAY" defaults, so old backups import cleanly.

ID remapping on backup import:
  Ivy's accommodateExistingAccountsAndCategories does a blunt
  string-replace of UUIDs across the entire backup JSON. This
  means UUIDs inside our CSV columns AND reservation references
  get remapped automatically for free.

9. GEMINI-SPECIFIC QUIRKS (learned the hard way)
================================================================

Gemini CANNOT execute Gradle in this environment. It tries
./gradlew, then .\gradlew, then cmd /c gradlew.bat — all fail
on Windows PowerShell. When it then claims "All tests passed
local verification", THAT IS A HALLUCINATION. You run the tests.

Specific failure modes we have caught:

  - Wrong source set: Gemini writes test files to src/main/java
    instead of src/androidTest/java. Symptom: "Unresolved
    reference 'kotest'" or "'junit'" on compileDebugKotlin.

  - Extra or missing closing brace at end of file. After each
    Gemini edit, open the file and check the last 3 lines.

  - Wildcard import rewrite: replaces ~40 specific imports with
    wildcard imports. NEVER accept this in existing files.

  - `not in` instead of `!in`.

  - `verify` instead of `coVerify`.

  - `HALF_DOWN` instead of `HALF_UP`.

  - Hand-written CREATE TABLE doesn't match the entity
    annotations. runMigrationsAndValidate names the mismatch.

  - Referring to a domain sealed interface (like
    BudgetPeriodType) from a Room entity — Room cannot
    auto-convert it. Use discriminator String + nullable params.

  - Chaining `.someField` off `shouldBeRight()` (or similar
    Either helpers) fails because the returned type is the
    sealed interface, not the concrete subtype. Always cast.

12. FUTURE PHASES (post-v1, DO NOT IMPLEMENT NOW)
================================================================

Phase 2 — Firebase Spark (free tier) — CLOUD + AMINA SHARING

  Goal: Me + Amina share the same budget and transactions
  across our phones.

  Platform: Firebase Spark (free tier) was chosen over Supabase
  and PocketBase because:
    - Google-native Android SDK
    - 50,000 MAU free auth
    - 20,000 writes/day free (we'll use <1%)
    - No auto-charge risk on Spark plan
    - Offline persistence built in
    - Reversible (Firestore data is portable)

  Firestore layout:
    workspaces/{workspaceId}/
      config/dynamic-budget
      accounts/{id}
      transactions/{id}
      categories/{id}
      reservations/{id}

  Key principles:
    - Sync SOURCE DATA only (transactions, config, reservations).
      NEVER sync the derived safe-to-spend number.
    - Security rules must restrict reads/writes to memberIds on
      the workspace document.
    - Last-write-wins conflict resolution for v1.
    - Offline-first: local Room stays the primary store. Firestore
      is a sync target.

  Estimated effort: 1-2 weeks (Tasks 24-29 post-v1).

  Requires a Migration 133→134 to add `workspaceId` to entities.
  Do NOT add workspaceId to any entity before Phase 2 begins.

Phase 3 — Sinking funds (far-future expenses)

  Problem: ReservationEntity currently subtracts the full amount
  out of TODAY's period capacity. Correct for bills due soon,
  wrong for bills due in months (e.g. April 5 bill entered in
  September would crash the September number).

  Desired: 1000 TND due April 5 (200 days away)
    → ~5 TND/day reduction in allowance, accumulating.
    → On April 5, the accumulated reserve hits 1000 and the user
      pays the bill from a pre-committed account.

  Two options:
    Option 1 (recommended): new SinkingFundEntity. Cleaner
      separation. New migration. Engine gains one input:
      dailySinkingContribution: Long.
    Option 2: extend ReservationEntity with
      spreadStartEpochDay: Long?. Smaller diff but blurs two
      concepts.

  Do NOT decide until Phase 1 is shipped and trusted.

Phase 4 — Loans with interest (mortgage, car loan)

  This is a TRACKER, not a budget input. User's explicit
  instruction:

    "Loan payments are PRE-COMMITTED fixed expenses. They are
     NOT part of safe-to-spend. They come out of income before
     the discretionary pool is defined. I pay them manually
     from an account EXCLUDED from includedAccountIds (or record
     them as a transfer from checking). Either way, the budget
     engine never sees them."

  Therefore: LoanEntity NEVER appears in BudgetEngineInput or
  DynamicBudgetConfig. Do NOT subtract loan payments from
  reservationsTotal or from capacity.

  Features:
    - Store loan terms: principal, annual rate, term (months),
      start date, payment frequency
    - Compute amortization schedule
    - Track remaining balance over time
    - Show total interest paid / projected
    - Show next payment date and amount
    - Optional reminder notification

  Detail screen:
    - Balance remaining
    - Next payment
    - Months remaining
    - Progress bar (principal paid / total principal)
    - Full amortization table (collapsible)

  Estimated effort: 2-3 weeks.

  Do NOT start before Phase 1 is trusted and Phase 2 works.
